  @Override
  public synchronized void lock() {
      if (locked) return;

      // try-with-resources 确保资源正确释放
      try (BasicOutputBuffer buffer = new BasicOutputBuffer();
           BsonBinaryWriter writer = new BsonBinaryWriter(buffer)) {

          BsonDocument bsonDoc = this.toBsonDocument(...);
          new BsonDocumentCodec().encode(writer, bsonDoc, ...);

          // 使用 lz4-java (与 C++ xxHash 兼容)
          byte[] bytes = buffer.toByteArray();
          this.integrityHash = XX_HASH_64.hash(bytes, 0, bytes.length, 0);
          this.locked = true;
      }
  }

  // document_integrity.cpp - C++ 方案 B 优化
  uint64_t computeDocumentHash(const BSONObj& doc) {

          return XXH64(afterHashElem, remainingSize, 0);
      }

  }

  → 服务器读取 1MB 内存 → 崩溃或泄露敏感数据

  问题 #1：size() 的来源

  // BSONElement::size() 的计算方式
  int BSONElement::size() const {
      // 根据 BSON 类型确定大小
      switch (type()) {
          case NumberDouble:  return 8;
          case NumberInt:     return 4;
          case NumberLong:    return 8;
          case Bool:          return 1;
          case String:
              // 从 BSON 字节中读取：前4字节是长度
              return 4 + ConstDataView(value()).read<LittleEndian<int32_t>>();
          case Object:
          case Array:
              // 从 BSON 字节中读取：前4字节是文档大小
              return ConstDataView(value()).read<LittleEndian<int32_t>>();
          // ...
      }
  }

  来源分析：
  - 固定类型（int, double, bool）：编译时常量，无风险
  - 变长类型（string, document）：从 BSON 原始字节 读取，理论上可被篡改

  但是，你说得对，需要看之前是否已验证：

  客户端 → 网络 → mongod 接收 → BSON 解析/验证 → write_ops_exec → computeDocumentHash
                                ↑
                           这里已经验证过

  MongoDB 在 message.cpp / bson_validate.cpp 中会验证 BSON 格式：
  - 检查总大小与声明大小一致
  - 检查元素边界不越界
  - 检查字符串以 \0 结尾

  结论：如果 BSON 已经通过标准验证路径，#1 风险很低。但如果有代码路径绕过验证直接调用 computeDocumentHash()，则有风险。可以加个防御性检查但不是必须的。

> 对时延影响如何 

● synchronized 时延分析

  理论开销

  | 场景             | 开销                           |
  |------------------|--------------------------------|
  | 无竞争（单线程） | ~20-50ns（偏向锁/轻量级锁）    |
  | 有竞争（多线程） | ~1-10μs（锁膨胀 + 上下文切换） |

  实际影响

  典型使用模式（无竞争）:
  // 单线程创建、填充、锁定、发送
  VerifiedDocument doc = new VerifiedDocument();  // 线程独占
  doc.put("a", 1);      // +20ns
  doc.put("b", 2);      // +20ns
  doc.put("c", 3);      // +20ns
  doc.lock();           // +20ns (已经是 synchronized)
  collection.insert(doc);

  总额外开销: ~80ns（4次锁获取）

  对比基准:
  | 操作                | 耗时       |
  |---------------------|------------|
  | synchronized 无竞争 | 20-50ns    |
  | xxHash64 计算 (1KB) | ~100ns     |
  | BSON 序列化         | ~1-10μs    |
  | 网络往返            | ~100μs-1ms |
  | 磁盘写入            | ~1-10ms    |

  结论

  | 维度               | 评估                                   |
  |--------------------|----------------------------------------|
  | 单线程使用         | 可忽略 - 占总时延 <0.01%               |
  | 多线程共享同一文档 | 不推荐这种用法，应该每线程创建独立实例 |
  | 是否需要优化       | 否 - 瓶颈在网络和磁盘 IO               |

  如果确实担心性能，可以用 ReentrantLock + tryLock() 做非阻塞检查，但实际场景中没必要。

  当前实现分析

  Status reservedFieldStatus = validateReservedHashField(doc);

  // validateReservedHashField 内部:

      return Status::OK();

  // 如果有 _$docHash:

  uint64_t computedHash = computeDocumentHash(doc); // 计算 hash

  时延影响

  | 场景                        | 修改前   | 修改后          | 增量               |
  |-----------------------------|----------|-----------------|--------------------|
  | 普通文档（无 _$docHash）    | 0        | hasField() 扫描 | +100-500ns         |
  | VerifiedDocument + 校验开启 | 1次 hash | 2次 hash！      | +100ns（重复计算） |
  | VerifiedDocument + 校验关闭 | 0        | 1次 hash        | +100ns（合理）     |

  问题：重复计算

  当校验开启时，hash 被计算了两次：

  validateReservedHashField(doc);  // 计算一次
  if (isIntegrityVerificationEnabled()) {
      verifyDocumentIntegrity(doc, ...);  // 又计算一次！
  }

  优化方案

  合并两个检查，避免重复工作：

  for (auto&& doc : wholeOp.documents) {
      Status integrityStatus = Status::OK();
      BSONObj docToInsert = doc;

      // 只检查一次
      if (doc.hasField(kDocHashFieldName)) {
          // 有 hash 字段 - 必须校验（无论是否启用全局校验）
          integrityStatus = verifyDocumentIntegrity(doc, IntegrityAction::kReject);
          if (integrityStatus.isOK()) {
              docToInsert = stripHashField(doc);
          }
      }
      // 无 hash 字段 - 正常处理，不需要额外检查

      // ... 继续处理
  }

  优化后时延:

  | 场景                     | 开销                  |
  |--------------------------|-----------------------|
  | 普通文档（无 _$docHash） | hasField() ~100-500ns |
  | VerifiedDocument         | 1次 hash ~100ns       |

● #3 错误处理逻辑问题

  当前代码流程

  for (auto&& doc : wholeOp.documents) {

          // 不加入 batch

  #6 参数类型不安全

      int actionMode = documentIntegrityActionMode.load();

  #10 编码效率

  文件: VerifiedDocument.java:93-94

  public synchronized void lock() {
      // 当前实现
      BsonDocument bsonDoc = this.toBsonDocument(BsonDocument.class, ...);  // 创建中间对象
      new BsonDocumentCodec().encode(writer, bsonDoc, ...);  // 再编码
  }

  问题：
  - toBsonDocument() 遍历所有字段，创建 BsonDocument
  - 然后 encode() 再次遍历 BsonDocument 写入 buffer
  - 两次遍历 + 一个中间对象 = 额外内存和 CPU

  优化思路:
  public synchronized void lock() {
      // 直接编码，无中间对象
      new DocumentCodec(getDefaultCodecRegistry())
          .encode(writer, this, EncoderContext.builder().build());
  }

  影响: 中等 - 对大文档有明显性能差异（~2x 遍历开销）

  #28 XX_HASH_64 线程安全性

  文件: VerifiedDocument.java:51

  private static final XXHash64 XX_HASH_64 = XXHashFactory.fastestInstance().hash64();

  问题：
  - 静态共享实例被多线程使用
  - 如果 XXHash64.hash() 内部有状态（如缓冲区），可能数据竞争

  实际情况：

  查看 lz4-java 源码：
  // net.jpountz.xxhash.XXHash64 接口
  public abstract long hash(byte[] buf, int off, int len, long seed);

  - 这是无状态方法，只读取输入 byte[]，不修改任何内部状态
  - XXHashFactory.fastestInstance().hash64() 返回的实现是线程安全的

  影响: 无 - lz4-java 的 XXHash64 是线程安全的

  结论: 这是误报，不需要修复
